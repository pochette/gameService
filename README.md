# Game Service

REST-сервис для хранения текущего состояния игроков, регистрации событий активности и аналитических запросов. Реализует обязательную часть тестового задания Java Developer: локальный запуск с PostgreSQL, сохранение произвольного JSON, неизменность страны пользователя и получение статистики.

Стек: Java 21, Spring Boot 4.1.1, Maven, Spring Data JPA, PostgreSQL, Liquibase. Для демонстрации предусмотрены Docker Compose и Swagger UI, для интеграционных тестов — Testcontainers.

## Быстрый запуск через Docker Compose

Потребуются Docker Desktop с Linux-контейнерами, Docker Compose и свободный порт 8080. JDK и Maven на компьютере для этого способа не нужны. При первой сборке необходим доступ к реестру Docker-образов и репозиториям Maven.

Из корня проекта:

```powershell
docker compose up --build -d
docker compose ps
docker compose logs -f app
```

Compose запускает PostgreSQL 17 и приложение. Приложение подключается после успешной проверки готовности БД; Liquibase создаёт таблицы и индексы автоматически. Дождитесь сообщения `Started GameServiceApplication` в логах. Выход из просмотра логов через Ctrl+C не останавливает контейнеры.

- API: http://localhost:8080
- Swagger UI: http://localhost:8080/swagger-ui/index.html
- OpenAPI: http://localhost:8080/v3/api-docs

PostgreSQL доступен приложению внутри Compose по адресу `postgres:5432`; порт БД на компьютер не опубликован. Для просмотра БД из контейнера:

```powershell
docker compose exec postgres psql -U postgres -d game_service
```

Остановка:

```powershell
docker compose down
```

Данные сохраняются в именованном томе `postgres_data` и доступны после повторного запуска. `docker compose down -v` удаляет том вместе с данными. Не запускайте одновременно приложение из IDE и Compose на одном порту 8080.

## Запуск приложения без Docker

Нужны JDK 21, работающий PostgreSQL и PowerShell для команд ниже. Maven устанавливать отдельно не требуется: в репозитории есть Maven Wrapper. На Linux/macOS используйте `./mvnw` вместо `.\mvnw.cmd`; примеры HTTP-запросов ниже написаны для PowerShell.

Запустите установленный PostgreSQL средствами вашей ОС. Настройки по умолчанию в [application.properties](src/main/resources/application.properties):

| Настройка | Значение | Переменная для переопределения |
| --- | --- | --- |
| URL БД | `jdbc:postgresql://localhost:5432/game_service` | `SPRING_DATASOURCE_URL` |
| Пользователь | `postgres` | `SPRING_DATASOURCE_USERNAME` |
| Пароль | `postgres` | `SPRING_DATASOURCE_PASSWORD` |

Если пользователь `postgres` уже существует, создайте БД один раз (при необходимости команда запросит пароль):

```powershell
psql -h localhost -U postgres -c "CREATE DATABASE game_service;"
```

Если пароль вашего PostgreSQL отличается, задайте его в текущей сессии:

```powershell
$env:SPRING_DATASOURCE_PASSWORD = 'your-local-password'
```

Сборка без запуска тестов и запуск собранного приложения:

```powershell
.\mvnw.cmd clean package -DskipTests
java -jar .\target\game-0.0.1-SNAPSHOT.jar
```

Альтернативный запуск из исходников:

```powershell
.\mvnw.cmd spring-boot:run
```

Liquibase создаёт структуру внутри существующей БД; саму БД нужно создать заранее. Hibernate проверяет соответствие схемы моделям (`ddl-auto=validate`). Данные находятся в PostgreSQL и сохраняются между перезапусками приложения.

## Правила API

### Состояние игрока

`userId` — UUID, который задаёт клиент в пути запроса. Состояние — JSON-объект с обязательными полями в корне:

| Поле | Допустимое значение |
| --- | --- |
| `money` | Целое JSON-число от `-9223372036854775808` до `9223372036854775807` (Java `long`) |
| `country` | От 1 до 255 латинских букв, шаблон `[A-Za-z]{1,255}` |

Числовые строки, дробные значения и `null` вместо обязательных значений отклоняются. Отрицательные значения `money` и `activity` допустимы: ТЗ ограничивает их диапазоном `long`.

Страна чувствительна к регистру: `US` и `us` различаются. Автоматической нормализации и проверки по справочнику стран нет. Ограничение длины согласовано с `VARCHAR(255)` и действует также для параметра `country` в аналитических запросах.

Размер тела запроса состояния в UTF-8 — не более 10 240 байт, включая пробелы и оформление JSON. Неизвестные поля сохраняются вместе со значениями, включая вложенные объекты, массивы и `null`. Порядок ключей и пробелы могут измениться при хранении в JSONB.

Первый успешный PUT создаёт пользователя и фиксирует серверное время создания. Каждый последующий успешный PUT полностью заменяет состояние: отсутствующие в новом JSON поля удаляются. UUID, исходная страна и время создания сохраняются. Попытка изменить страну возвращает 409 без изменения прежнего состояния.

### События и периоды

Каждый POST с обязательным целым полем `activity` в диапазоне Java `long` создаёт отдельное событие для существующего пользователя. Повтор того же запроса создаёт ещё одно событие. Время получения назначает сервер.

Параметры `from` и `to` обязательны и задаются в ISO 8601 с часовым смещением, например `2026-01-01T00:00:00Z`. Интервал — `[from, to)`: нижняя граница включается, верхняя исключается; обязательно `from < to`. При передаче положительного смещения в URL знак `+` нужно кодировать как `%2B`.

### Эндпоинты

| Метод и путь | Результат успешного запроса |
| --- | --- |
| `PUT /users/{userId}/state` | 200 без тела; создание или полная замена состояния |
| `GET /users/{userId}/state` | 200, объект с `userId` и `state` |
| `POST /users/{userId}/activities` | 200 без тела; новое событие |
| `GET /users/{userId}/activities?from=...&to=...` | 200, массив объектов с `userId`, `activity`, `receivedAt`, по времени по возрастанию |
| `GET /users/top?country=US&limit=10` | 200, массив объектов с `userId` и `money` |
| `GET /statistics/new-users?country=US&from=...&to=...` | 200, JSON-число — количество новых пользователей |

В топе обязательны `country` и целочисленный `limit` от 1 до 100. Сортировка: `money` по убыванию, при равенстве — UUID по возрастанию. Учитывается текущий баланс.

Новый пользователь определяется по первому успешному сохранению состояния. Повторный PUT не увеличивает количество новых пользователей. При отсутствии совпадений топ и список событий возвращают `[]`, статистика новых пользователей — `0`. Чтение состояния, запись и чтение активности неизвестного пользователя возвращают 404.

## Примеры запросов

Выполняйте блоки последовательно в одной сессии PowerShell после запуска приложения. Демонстрационные записи создаются запросами, автоматического наполнения БД нет. Для проверки точных результатов топа и количества пользователей используйте БД без других пользователей стран US и CA.

### 1. Создание пользователей — PUT /users/{userId}/state

```powershell
$base = 'http://localhost:8080'
$userId = '10000000-0000-0000-0000-000000000001'
$states = @(
    @{ id = $userId; body = '{"money":2000,"country":"US","level":17,"inventory":{"sword":2,"potion":5}}' },
    @{ id = '10000000-0000-0000-0000-000000000002'; body = '{"money":2000,"country":"US","level":12}' },
    @{ id = '10000000-0000-0000-0000-000000000003'; body = '{"money":1000,"country":"US","level":3}' },
    @{ id = '10000000-0000-0000-0000-000000000004'; body = '{"money":9000,"country":"CA","level":25}' }
)
foreach ($state in $states) {
    Invoke-RestMethod -Method Put -Uri "$base/users/$($state.id)/state" `
        -ContentType 'application/json' -Body $state.body
}
```

Каждый успешный запрос возвращает 200 без тела. Повторный запуск обновляет эти же записи.

### 2. Чтение состояния — GET /users/{userId}/state

```powershell
Invoke-RestMethod "$base/users/$userId/state" | ConvertTo-Json -Depth 20
```

Ожидаемый JSON (порядок ключей несущественен):

```json
{
  "userId": "10000000-0000-0000-0000-000000000001",
  "state": {
    "money": 2000,
    "country": "US",
    "level": 17,
    "inventory": {"sword": 2, "potion": 5}
  }
}
```

### 3. Запись активности — POST /users/{userId}/activities

```powershell
Invoke-RestMethod -Method Post -Uri "$base/users/$userId/activities" `
    -ContentType 'application/json' -Body '{"activity":42}'
Invoke-RestMethod -Method Post -Uri "$base/users/$userId/activities" `
    -ContentType 'application/json' -Body '{"activity":100}'
```

Оба запроса возвращают 200 без тела. Каждый повтор добавляет новые события.

### 4. Чтение активности — GET /users/{userId}/activities

```powershell
$from = '2000-01-01T00:00:00Z'
$to = '2100-01-01T00:00:00Z'
Invoke-RestMethod "$base/users/$userId/activities?from=$from&to=$to" |
    ConvertTo-Json -Depth 20
```

При первом выполнении на новой БД ожидаются два объекта: `activity` 42 и 100, `userId` первого игрока и `receivedAt` с фактическим серверным временем. Список упорядочен по времени по возрастанию. Период выбран широким, чтобы включить события демонстрации.

### 5. Топ по стране — GET /users/top

```powershell
Invoke-RestMethod "$base/users/top?country=US&limit=2" | ConvertTo-Json -Depth 20
```

При наличии только демонстрационных данных:

```json
[
  {"userId":"10000000-0000-0000-0000-000000000001","money":2000},
  {"userId":"10000000-0000-0000-0000-000000000002","money":2000}
]
```

Пользователь CA исключён, несмотря на больший баланс. Равные балансы упорядочены по UUID.

### 6. Новые пользователи — GET /statistics/new-users

```powershell
Invoke-RestMethod "$base/statistics/new-users?country=US&from=$from&to=$to"
```

Ожидается число `3`, если других пользователей US в периоде нет. Повторные PUT не меняют этот результат.

### 7. Полная замена состояния

Продолжите после проверки топа. Баланс первого пользователя изменится и повлияет на последующие запросы топа.

```powershell
Invoke-RestMethod -Method Put -Uri "$base/users/$userId/state" `
    -ContentType 'application/json' `
    -Body '{"money":2500,"country":"US","inventory":{"potion":10},"custom":{"enabled":true}}'
Invoke-RestMethod "$base/users/$userId/state" | ConvertTo-Json -Depth 20
```

Ожидаемое `state`:

```json
{"money":2500,"country":"US","inventory":{"potion":10},"custom":{"enabled":true}}
```

Прежние `level` и `inventory.sword` отсутствуют. Записанные события активности сохраняются независимо от состояния.

### 8. Запрет смены страны

```powershell
try {
    Invoke-RestMethod -Method Put -Uri "$base/users/$userId/state" `
        -ContentType 'application/json' -Body '{"money":9999,"country":"CA"}'
} catch {
    if ($null -ne $_.Exception.Response) {
        Write-Output ("HTTP {0}" -f [int]$_.Exception.Response.StatusCode)
    }
    Write-Output $_.ErrorDetails.Message
}
Invoke-RestMethod "$base/users/$userId/state" | ConvertTo-Json -Depth 20
```

Ожидается HTTP 409 с кодом `COUNTRY_IMMUTABLE`. GET возвращает состояние из предыдущего шага: баланс 2500, страну US, `inventory` и `custom` без изменений.

## Ошибки

Обрабатываемые ошибки валидации и предметной области возвращаются в едином формате:

```json
{"code":"USER_NOT_FOUND","message":"Пользователь не найден"}
```

| HTTP | Ситуация | Код ошибки |
| --- | --- | --- |
| 400 | Ошибка разбора JSON | `INVALID_JSON` или `INVALID_REQUEST`, в зависимости от этапа обработки |
| 400 | Неверный UUID, отсутствующий параметр, нарушение ограничений параметров | `INVALID_REQUEST` |
| 400 | Неверные поля состояния/активности или порядок границ периода | `INVALID_ARGUMENT` либо `INVALID_REQUEST`, в зависимости от проверки |
| 404 | Неизвестный пользователь | `USER_NOT_FOUND` |
| 409 | Попытка изменить страну | `COUNTRY_IMMUTABLE` |
| 413 | Тело состояния больше 10 240 байт | `STATE_TOO_LARGE` |

Проверки входных данных выполняются до записи. Сохранение состояния и запись активности выполняются в транзакциях; отказ в смене страны не изменяет ранее сохранённые данные.

## Модель данных и индексы

Миграции находятся в [src/main/resources/db/changelog](src/main/resources/db/changelog). Главный файл — [db.changelog-master.yaml](src/main/resources/db/changelog/db.changelog-master.yaml); он сначала создаёт `users`, затем `activities` с внешним ключом.

| Таблица | Колонка | Тип и назначение |
| --- | --- | --- |
| `users` | `id` | `UUID`, первичный ключ, идентификатор клиента |
| `users` | `money` | `BIGINT`, текущий баланс для аналитики |
| `users` | `country` | `VARCHAR(255)`, исходная неизменяемая страна |
| `users` | `state` | `JSONB`, полное текущее состояние |
| `users` | `created_at` | `TIMESTAMP(6) WITH TIME ZONE`, серверное время первого сохранения |
| `activities` | `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY`, первичный ключ события |
| `activities` | `user_id` | `UUID`, внешний ключ на `users(id)` |
| `activities` | `activity` | `BIGINT`, значение события |
| `activities` | `received_at` | `TIMESTAMP(6) WITH TIME ZONE`, серверное время получения |

Все перечисленные колонки обязательны (`NOT NULL`). `money` и `country` выделены из JSON в отдельные колонки для аналитических запросов. Баланс и JSON обновляются одним SQL-запросом.

| Индекс | Назначение |
| --- | --- |
| `users(country, money DESC, id ASC)` | Фильтрация топа по стране, сортировка по балансу и UUID |
| `users(country, created_at)` | Подсчёт новых пользователей страны за период |
| `activities(user_id, received_at)` | Выборка событий пользователя за период с сортировкой по времени |

Первичные ключи также индексируются PostgreSQL. Фильтрация, сортировка, ограничение топа и подсчёт выполняются в БД. Приложение преобразует уже выбранные записи в DTO.

## Структура и одновременные запросы

Код разделён на пакеты `user`, `activity`, `statistic` и общие компоненты `common`. Контроллеры принимают и проверяют запросы, сервисы реализуют операции, репозитории обращаются к PostgreSQL. Общий обработчик формирует ошибки API.

Состояние сохраняется атомарным `INSERT ... ON CONFLICT (id) DO UPDATE`. При совпадении UUID обновление выполняется только при совпадении страны; меняются `money` и `state`, а `country` и `created_at` сохраняются.

При одновременных PUT одного UUID с одинаковой страной оба запроса могут завершиться успешно. Итоговое состояние соответствует последней записи в БД целиком. Порядок отправки HTTP-запросов не гарантирует порядок записи. При конкурентном создании UUID с разными странами один запрос создаёт пользователя, а другой получает 409.

## Тесты

Для запуска тестов на компьютере нужен JDK 21. Полный набор:

```powershell
.\mvnw.cmd test
```

`UserApiIntegrationTest` автоматически запускает отдельный PostgreSQL 17 через Testcontainers и приложение на случайном порту. Нужен работающий Docker с Linux-контейнерами. Запускать приложение или Compose вручную для этих тестов не требуется.

`GameServiceApplicationTests.contextLoads` использует БД из `application.properties` или переменных окружения. Поэтому полный набор дополнительно требует доступного PostgreSQL и заранее созданной БД (по умолчанию `localhost:5432/game_service`). При загрузке контекста запускаются миграции. PostgreSQL внутри Compose без публикации порта не заменяет эту БД.

Основные проверки без зависимости от локального PostgreSQL:

```powershell
.\mvnw.cmd "-Dtest=UserServiceTest,UserApiIntegrationTest" test
```

Только юнит-тесты, без Docker и БД:

```powershell
.\mvnw.cmd "-Dtest=UserServiceTest" test
```

Покрытие обязательных сценариев ТЗ:

| Сценарий | Автоматическая проверка |
| --- | --- |
| Первое сохранение и создание пользователя | `shouldCreateUser` |
| Повторное обновление и GET последнего состояния с неизвестными полями | `shouldReplaceStateAndReturnLatestState` |
| Ошибка валидации | `shouldRejectMissingMoney` и `shouldValidateCountryLengthWithoutChangingSavedState` |
| Запрет смены страны без изменения прежнего состояния | `shouldRejectCountryChangeWithoutChangingSavedState` |
| Аналитический запрос с ожидаемым результатом | Интеграционный `shouldReturnTopUsers`: страна, баланс, порядок UUID, limit |

Дополнительно проверяются передача JSON в `upsertState`, обработка отказа репозитория, параметры сортировки топа и конкурентное сохранение. Интеграционная проверка длины страны принимает 255 букв и отклоняет 256 без изменения данных. При обновлении и отклонении смены страны проверяется неизменность времени создания.

Конкурентный тест `shouldSaveSameUserConcurrently` синхронизирует старт двух PUT и проверяет оба ответа 200, целостность итогового JSON и его согласованность с балансом. Он не гарантирует определённое чередование операций на сервере и не проверяет гонку разных стран.

Проверка от 10 октября 2026 года: `.\mvnw.cmd test` — 11 тестов, 0 ошибок, 0 падений, 0 пропусков (4 юнит-теста, 6 интеграционных и 1 проверка контекста).

## Известные ограничения

- Автоматические тесты покрывают минимальные обязательные сценарии ТЗ, но не все ветви API. Нет отдельных тестов записи/чтения активности, подсчёта новых пользователей, границ времени, размера 10 240 байт и всех вариантов ошибочных запросов.
- Список активности за период возвращается целиком, без пагинации. Удаление старых событий и срок хранения не реализованы.
- Полный набор тестов зависит от локальной БД из-за `contextLoads`; основные тесты изолированы через Testcontainers.
- Swagger UI доступен для просмотра API; точные JSON-примеры состояния приведены выше, поскольку контроллер принимает тело состояния как массив байтов для проверки размера.
- Дополнительная часть для Middle с оценкой нагрузки не включена. Высоконагруженная и распределённая архитектура не реализовывалась; обязательная часть ТЗ рассчитана на локальный запуск.
