# Game Service

REST-сервис хранения состояния игроков, событий активности и аналитики по ним.

**Стек:** Java 21, Spring Boot 4.1.1, Maven, PostgreSQL, Spring Data JPA, Liquibase. Есть Docker Compose, Swagger UI и тесты с Testcontainers.

## Запуск

Все команды ниже выполняются из корня проекта в PowerShell.

### Docker Compose

Нужны Docker Desktop с Linux-контейнерами, Docker Compose и свободный порт 8080. При первой сборке нужен интернет для загрузки образов и зависимостей.

```powershell
docker compose up --build -d
docker compose logs -f app
```

Compose запускает PostgreSQL 17 и приложение; Liquibase создаёт структуру БД. Дождитесь `Started GameServiceApplication` в логах.

- API: http://localhost:8080
- Swagger UI: http://localhost:8080/swagger-ui/index.html

Остановка: `docker compose down`. Данные сохраняются в томе `postgres_data`; добавление `-v` удаляет их. Порт PostgreSQL на компьютер не опубликован.

### Локально

Нужны JDK 21 и запущенный PostgreSQL. Maven предоставляется Wrapper-скриптом. По умолчанию используется БД `game_service` на `localhost:5432`, пользователь и пароль — `postgres`.

```powershell
# Создать БД один раз; пользователь postgres должен существовать
psql -h localhost -U postgres -c "CREATE DATABASE game_service;"

# Собрать без тестов и запустить
.\mvnw.cmd clean package -DskipTests
java -jar .\target\game-0.0.1-SNAPSHOT.jar
```

Настройки: [application.properties](src/main/resources/application.properties). Переопределение — через `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`. Например: `$env:SPRING_DATASOURCE_PASSWORD = 'your-password'`.

Liquibase создаёт таблицы в существующей БД. Данные сохраняются между перезапусками. Не запускайте локальное приложение и Compose одновременно на порту 8080. На Linux/macOS вместо `.\mvnw.cmd` используйте `./mvnw`.

## Контракт API

- `userId` — UUID клиента. Состояние — JSON-объект с обязательными корневыми полями `money` (целое число Java `long`) и `country` (1–255 латинских букв). Регистр страны значим, проверки по справочнику стран нет.
- Тело состояния — максимум 10 240 байт в UTF-8. Неизвестные поля сохраняются, включая вложенные значения; пробелы и порядок ключей могут меняться.
- Первый PUT создаёт пользователя. Повторный PUT полностью заменяет состояние, сохраняя страну и серверное время создания. Смена страны отклоняется без изменения данных.
- `activity` — обязательное целое число Java `long`. Каждый POST создаёт отдельное событие существующего пользователя с серверным временем получения. Числовые строки и дробные значения отклоняются; отрицательные целые допустимы.
- `from` и `to` обязательны: ISO 8601 со смещением, интервал `[from, to)`, `from < to`. Знак `+` в смещении URL кодируется как `%2B`.
- Для топа обязательны `country` и целочисленный `limit` от 1 до 100. Сортировка: текущий `money` по убыванию, при равенстве — UUID по возрастанию.

| Метод и путь | Успешный ответ (HTTP 200) |
| --- | --- |
| `PUT /users/{userId}/state` | Без тела |
| `GET /users/{userId}/state` | Объект с `userId` и `state` |
| `POST /users/{userId}/activities` | Без тела |
| `GET /users/{userId}/activities?from=...&to=...` | Массив с `userId`, `activity`, `receivedAt`, по времени по возрастанию |
| `GET /users/top?country=US&limit=10` | Массив с `userId` и `money` |
| `GET /statistics/new-users?country=US&from=...&to=...` | `{"count": N}` — число впервые созданных пользователей за период |

При отсутствии результатов списки возвращают `[]`, количество — `{"count": 0}`. Повторный PUT не увеличивает число новых пользователей. Чтение состояния, запись и чтение активности неизвестного пользователя возвращают 404.

Ошибки валидации и предметной области имеют формат `{"code":"...","message":"..."}`: некорректный запрос — **400**, неизвестный пользователь — **404** (`USER_NOT_FOUND`), смена страны — **409** (`COUNTRY_IMMUTABLE`), превышение размера состояния — **413** (`STATE_TOO_LARGE`).

## Примеры всех эндпоинтов

Выполните блок в одной сессии после запуска приложения. Он создаёт пользователя со случайным UUID и одно событие; на пустой БД топ содержит этого пользователя, число новых пользователей US равно 1.

```powershell
$base = 'http://localhost:8080'
$id = [guid]::NewGuid().ToString()
$from = '2000-01-01T00:00:00Z'
$to = '2100-01-01T00:00:00Z'

# Создать состояние — 200 без тела
Invoke-RestMethod -Method Put -Uri "$base/users/$id/state" `
    -ContentType 'application/json' `
    -Body '{"money":1500,"country":"US","level":17,"inventory":{"sword":2}}'

# Получить state с money, country, level и inventory
Invoke-RestMethod "$base/users/$id/state" | ConvertTo-Json -Depth 20

# Добавить событие — 200 без тела
Invoke-RestMethod -Method Post -Uri "$base/users/$id/activities" `
    -ContentType 'application/json' -Body '{"activity":42}'

# Получить событие 42 с userId и серверным receivedAt
Invoke-RestMethod "$base/users/$id/activities?from=$from&to=$to" |
    ConvertTo-Json -Depth 20

# Топ и число новых пользователей US
Invoke-RestMethod "$base/users/top?country=US&limit=10" | ConvertTo-Json -Depth 20
Invoke-RestMethod "$base/statistics/new-users?country=US&from=$from&to=$to"

# Полная замена: level и inventory должны исчезнуть из state
Invoke-RestMethod -Method Put -Uri "$base/users/$id/state" `
    -ContentType 'application/json' -Body '{"money":2000,"country":"US","custom":true}'
Invoke-RestMethod "$base/users/$id/state" | ConvertTo-Json -Depth 20
```

Повтор блока создаёт ещё одного пользователя. Другие записи US также участвуют в аналитике. Для проверки запрета смены страны отправьте PUT тому же UUID с `country: "CA"`: ожидается 409, а последующий GET должен вернуть прежнее состояние.

## Хранение данных

[Миграции Liquibase](src/main/resources/db/changelog/db.changelog-master.yaml) создают две таблицы; все колонки обязательны:

- `users`: `id UUID` (PK), `money BIGINT`, `country VARCHAR(255)`, `state JSONB`, `created_at TIMESTAMP(6) WITH TIME ZONE`.
- `activities`: `id BIGINT IDENTITY` (PK), `user_id UUID` (FK → `users.id`), `activity BIGINT`, `received_at TIMESTAMP(6) WITH TIME ZONE`.

Баланс и страна выделены из JSON для аналитики. Фильтрация, сортировка, ограничение топа и подсчёт выполняются в PostgreSQL.

| Индекс | Назначение |
| --- | --- |
| `users(country, money DESC, id ASC)` | Топ по стране с нужной сортировкой |
| `users(country, created_at)` | Новые пользователи страны за период |
| `activities(user_id, received_at)` | События пользователя за период по времени |

Сохранение использует транзакцию и атомарный `INSERT ... ON CONFLICT (id) DO UPDATE`: баланс и JSON обновляются вместе, только при совпадении страны. При конкурентных PUT одной страны сохраняется последнее записанное БД состояние целиком; порядок отправки запросов не определяет порядок записи. Исходные страна и время создания не меняются.

### Проверки API через Postman

В репозитории добавлена [коллекция Postman](postman/game-service.postman_collection.json) с 28 запросами и автоматическими проверками ответов для всех шести эндпоинтов.

Для запуска:

1. Запустите приложение и PostgreSQL.
2. Импортируйте коллекцию в Postman через **Import**.
3. Проверьте переменную коллекции `baseUrl` (по умолчанию `http://localhost:8080`).
4. Запустите все запросы по порядку через **Run collection**, одну итерацию.

Первый запрос генерирует новые UUID, уникальный буквенный идентификатор страны и временной интервал вокруг текущего времени. Проверки не зависят от ранее созданных игроков; тестовые записи остаются в БД после выполнения коллекции.

Проверяются создание и полная замена состояния с сохранением неизвестных полей; запрет смены страны без изменения данных; запись двух отдельных событий и их порядок по времени; пустая история существующего пользователя; топ, ограничение количества результатов и порядок UUID при равных балансах; подсчёт новых пользователей без увеличения при обновлении состояния.

Негативные сценарии проверяют неизвестного пользователя (404), смену страны (409), некорректный UUID, отсутствие обязательных полей, неверный тип денег, некорректные limit и период, повреждённый JSON (400), превышение размера состояния (413). После ошибочных PUT проверяется неизменность сохранённого состояния.

**Все проверки коллекции успешно пройдены 10.10.2026.** Результат подтверждён ручным запуском коллекции в Postman; эти проверки дополняют тесты JUnit и Testcontainers.

## Исправление проблемы конкурентности

Во время тестирования обнаружена гонка при одновременном первом сохранении одного UUID. В исходной реализации проверка существования пользователя и сохранение выполнялись отдельно: два запроса могли одновременно увидеть отсутствие записи и попытаться создать её. Одной транзакции вокруг этой последовательности было недостаточно для устранения гонки.

Проблема решена переходом на атомарный PostgreSQL UPSERT (`INSERT ... ON CONFLICT (id) DO UPDATE`). Конфликт UUID обрабатывается в БД: при одинаковой стране состояние обновляется целиком, при другой — запрос отклоняется с 409. Баланс и JSON сохраняются согласованно, исходные страна и время создания не меняются.

Интеграционный тест `shouldSaveSameUserConcurrently` запускает два PUT нового UUID с одинаковой страной и разными состояниями. После исправления оба запроса возвращают 200; итоговый JSON соответствует одному из запросов целиком, а баланс в отдельной колонке совпадает с балансом в JSON. Тест прошёл в последнем полном прогоне. Он синхронизирует старт запросов, но не гарантирует конкретное чередование операций на сервере.

## Выполнение ТЗ и границы проверки

В приложении реализована обязательная функциональность ТЗ:

- Все шесть REST-эндпоинтов: сохранение и чтение состояния, запись и чтение активности, топ по стране и подсчёт новых пользователей.
- Сохранение неизвестных полей JSON, полная замена состояния, неизменность страны и времени создания, серверное время событий.
- Проверка входных данных, размера состояния и параметров периода, обработка неизвестного пользователя и ошибок в едином JSON-формате.
- Хранение в PostgreSQL между перезапусками, миграции, ключи и индексы; аналитические операции выполняются запросами к БД.
- Инструкции сборки, запуска и тестирования, настройки подключения и примеры всех эндпоинтов в README. Дополнительно предоставлены Docker Compose, Swagger UI и Testcontainers — ТЗ не делает их обязательными.

**Все пять минимальных тестовых сценариев ТЗ покрыты:** создание пользователя; обновление и получение последнего состояния с неизвестными полями; ошибка валидации; отказ в смене страны без изменения данных; аналитический запрос с проверкой результата. Для аналитического сценария выбран топ по стране. ТЗ требует хотя бы один такой запрос и прямо указывает, что полное покрытие не требуется.

### Что не включено в обязательный объём

- Отдельные автоматические тесты записи/чтения активности, подсчёта новых пользователей, границ периода, размера тела и всех ошибок API не добавлены: ТЗ не требует отдельного теста для каждой операции или ошибки. Сама эта функциональность обязательна и реализована; текущий набор тестов не подтверждает все её ветви.
- Проверка конкурентных запросов с разными странами не добавлена: отдельного требования к такому тесту нет. Дополнительный конкурентный тест проверяет два запроса с одинаковой страной.
- Пагинация событий и удаление старой статистики не реализованы: обязательная часть ТЗ их не предусматривает. Поэтому события за период возвращаются целиком и накапливаются без автоматической очистки.
- Дополнительная часть Middle с оценкой нагрузки не выполнена: в ТЗ она обозначена как необязательная. Высоконагруженная и распределённая архитектура также не требуется для обязательной части.

Практическое ограничение текущей настройки: полный набор тестов требует локальной БД для `contextLoads`; основные проверки запускаются отдельно с PostgreSQL в Testcontainers. Успешный прогон подтверждает перечисленные тестовые сценарии, а не исчерпывающую проверку всей реализации.
### Часть для Middle-разработчика

Исходные данные: 10 млн игроков, 500 тыс. активных в сутки, каждый сохраняет состояние 50 раз и отправляет 500 событий.

Сохранение состояния: 500 тыс. игроков * 50 сохранений = 25 млн в сутки, примерно 290 RPS.
Сохранение activity: 500 тыс. игроков * 500 событий = 250 млн в сутки, примерно 2 893 RPS.

Общая нагрузка: 290 + 2 893 = 3 183 RPS.

Игроки находятся в разных часовых поясах, поэтому нагрузка распределена по суткам относительно равномерно. В пиках (обновления, ивенты и др.) она может быть в 2-3 раза выше среднего, до 10 тыс. RPS.

Основная нагрузка приходится на запись активности. Само значение activity занимает всего 8 байт (Java long), но вместе с user_id, временем, служебными данными строки PostgreSQL и индексами выходит примерно 135 байт на событие.
В сутки это примерно 34 ГБ, около 1 ТБ в месяц и более 10 ТБ в год.

Таблица users практически не растёт, так как существующие строки только обновляются. Размер данных: 10 млн строк по 2 КБ (допущение), всего около 20 ГБ.

#### Ограничения нынешнего решения

- Используется одна база PostgreSQL. События копятся без очистки, партиционирование и шардирование не настроены.
- История событий отдаётся целиком, без пагинации. За месяц у одного игрока набирается около 15 тыс. событий, и все они уходят одним ответом.
- Каждое событие записывается отдельным запросом и отдельной транзакцией, пакетной вставки нет.
- Перед сохранением события пользователь загружается из базы целиком, вместе с JSON состояния, хотя нужно только проверить, что он существует.
- Если ответ сервера потерялся в сети, клиент повторит запрос, и событие запишется дважды. Защиты от дублей нет.
- Игрок может играть с разных устройств (консоль, ПК, телефон). Сейчас последнее сохранение просто перезаписывает предыдущее, и прогресс с другого устройства может потеряться.

#### Дальнейшее развитие

- Проверять существование пользователя через `existsById` и не загружать состояние при записи события.
- Добавить пагинацию истории событий: отдавать страницами и продолжать с последней записи (keyset), а не через OFFSET.
- Принимать события пачками (`POST /users/{userId}/activities/batch`) и вставлять в базу пакетно. Так запросов к серверу и транзакций становится в десятки раз меньше.
- Партиционировать таблицу activities по времени (например, по месяцам) и удалять старые партиции целиком, например старше 90 дней. Это быстрее, чем `DELETE`, и не нагружает базу.
- Клиент присваивает каждому событию свой `eventId`, а сервер запоминает уже принятые id в Redis на сутки. Повторный запрос с тем же id не создаёт дубль.
- Хранить версию состояния, которую клиент присылает при сохранении. Если версия устарела, сервер возвращает ошибку, и клиент сначала загружает актуальное состояние. Это защищает от потери данных при игре с разных устройств.
- Добавить брокер сообщений (ActiveMQ, RabbitMQ или Kafka) между API и базой. API принимает события и кладёт их в очередь, а отдельные обработчики пакетно пишут их в базу. Так сглаживаются пики, и база не получает тысячи мелких транзакций в секунду.
- Использовать Redis для топа игроков по стране (Sorted Set на каждую страну), кеша состояния и ограничения частоты запросов. Это снимет с базы основную нагрузку на чтение.
- При дальнейшем росте вынести данные в NoSQL: состояние игрока хорошо подходит для документной базы (MongoDB), а события — для Cassandra, где их удобно читать по игроку и периоду и удалять через TTL.
- Добавить горизонтальное масштабирование. Сервис не хранит состояние между запросами, поэтому его можно запускать в нескольких экземплярах за балансировщиком. Так как игроки расположены по всему миру, логично развернуть сервис в нескольких регионах и направлять игрока в ближайший. Страна у игрока не меняется, поэтому по ней можно определять, в каком регионе хранить его данные. Это уменьшит задержки и упростит соблюдение требований к хранению персональных данных в разных странах.
